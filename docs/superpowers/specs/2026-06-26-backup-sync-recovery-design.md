# Account Backup, Sync & Recovery Design

## Overview

Self-sovereign identity system for Mess&Anger. Zero-knowledge, no email/phone required.  
User controls their keys via encrypted backup file. Multi-device sync via P2P mesh.

## Key Hierarchy

```
Master Seed (256-bit entropy)
├── AES-256-GCM Master Key (storage encryption, exists today)
├── X25519 Identity Keypair (master public key = user ID, NEW)
├── Ed25519 Signing Keypair (signs device keys, NEW)
└── HKDF → per-device sub-keys
```

- Master seed is generated at first launch
- Encoded as 24-word mnemonic (BIP39-style, replaces current 10-word)
- Stored encrypted in IndexedDB (existing `deviceSecurity.ts` pattern)
- The X25519 public key is the user's global identifier (no email/phone/username)

## Backup File Format (.mabak)

Binary file, versioned, single-file self-contained.

### Structure

```
┌─────────────────────────┐
│ Magic: "MABAK\0" (6b)   │
│ Version: uint8 (1b)     │
│ Flags: uint8 (1b)       │
│  bit0: hasTOTP          │
│  bit1-7: reserved       │
│ Salt: 32 bytes          │
│ IV: 12 bytes            │
│ Encrypted Payload        │
│ HMAC-SHA256: 32 bytes   │
└─────────────────────────┘
```

### Key Derivation

```
base_key = PBKDF2(password, salt, 600000, 256, SHA-256)
if hasTOTP:
  totp_key = PBKDF2(password + TOTP_code, salt, 600000, 256, SHA-256)
  enc_key = SHA-256(base_key || totp_key)
else:
  enc_key = base_key

payload_key = HKDF-SHA256(enc_key, "mabak-payload", 256)
hmac_key = HKDF-SHA256(enc_key, "mabak-hmac", 256)
```

### Encrypted Payload (AES-256-GCM)

```json
{
  "version": 1,
  "createdAt": "ISO8601",
  "masterSeed": "hex-encrypted",
  "identity": {
    "x25519Private": "hex-encrypted",
    "x25519Public": "hex",
    "ed25519Private": "hex-encrypted",
    "ed25519Public": "hex"
  },
  "devices": [
    {
      "id": "device-id",
      "name": "string",
      "x25519Public": "hex",
      "x25519Private": "hex-encrypted",
      "createdAt": "ISO8601"
    }
  ],
  "settings": { "..." },
  "chats": [ { "id", "name", "participants", "..." } ],
  "contacts": [ { "publicKey", "name", "..." } ],
  "channels": [ { "..." } ],
  "bots": [ { "..." } ],
  "ratchetStates": [ { "chatId", "state": "encrypted-per-device" } ]
}
```

Private keys within the payload are further encrypted with AES-256-GCM using a key derived from the master seed itself (defense in depth — even with backup password, private keys are additionally protected).

## Two-Factor Verification (TOTP)

### Setup
- On first device: generate TOTP secret (SHA-256, 6 digits, 30s)
- Show QR code for authenticator app (Google Authenticator, Authy, etc.)
- Store TOTP secret encrypted in the backup (and in IndexedDB locally)

### Usage
1. **Backup encryption**: TOTP code concatenated with password → PBKDF2 key derivation
2. **Device pairing**: new device must provide a valid TOTP code during pairing (verified by already-paired device)
3. **Restore**: entering backup password + current TOTP code to decrypt

### Recovery if 2FA device lost
- The mnemonic phrase bypasses TOTP entirely — it directly encodes the master seed
- User can restore from mnemonic, then set up new TOTP

## Device Pairing Protocol

### Flow

```
Device A (has account)          Device B (new)
     │                              │
     │  1. "Pair Device" in UI      │
     │────── QR Code ──────────────►│  QR: signaling URL + device A pubkey
     │                              │      + session token (encrypted)
     │                              │  2. Connect to signaling server
     │                              │  3. Send { deviceBPubKey, signed(deviceBPubKey, masterKey) }
     │◄──── P2P Channel ────────────│  4. Verify signature with master pubkey
     │  5. Accept/Deny in UI        │
     │────── Sync Start ───────────►│  6. Full state sync via P2P
     │                              │
```

### Security
- QR code encrypted with ephemeral X25519 key (generated by Device A for this pairing)
- Signatures prove device B is authorized by master key
- Optional TOTP challenge during steps 4-5

## P2P Sync Protocol

### Transport
- Existing WebRTC mesh via signaling server (reuse `P2PNetwork`, `MeshRouter`)
- New sync message type: `MSG_SYNC_STATE` / `MSG_SYNC_REQUEST` / `MSG_SYNC_ACK`

### Message Types

| Type | Payload | Direction |
|------|---------|-----------|
| `SYNC_REQUEST` | `{ lastSyncTimestamp }` | New device → existing |
| `SYNC_STATE` | `{ entityType, entityId, encryptedBlob, timestamp }` | Both directions |
| `SYNC_ACK` | `{ entityId, timestamp }` | Both directions |
| `SYNC_CONFLICT` | `{ entityId, yourVersion, myVersion }` | Both directions |

### Sync Units
Each entity (chat, message, contact, setting) syncs independently:

```
{
  "entityType": "chat" | "message" | "contact" | "setting" | "channel" | "bot",
  "entityId": "string",
  "encryptedBlob": "AES-256-GCM(JSON blob, masterKey)",
  "timestamp": "ISO8601",
  "deviceId": "originating device"
}
```

### Conflict Resolution
- Per-entity last-write-wins (by timestamp)
- For collections (chat list, contacts): merge strategy — union of items, last-write-wins per item
- If timestamps are equal (within 1s tolerance): device ID tiebreaker (lexicographic)

### Initial Sync (New Device)
1. New device connects via P2P to each online device
2. Sends `SYNC_REQUEST` with zero timestamp
3. Each online device sends `SYNC_STATE` for every entity it has
4. New device deduplicates by entity ID + highest timestamp
5. Acknowledges with `SYNC_ACK`

### Incremental Sync
1. Device broadcasts `SYNC_REQUEST` with `lastSyncTimestamp`
2. Online devices send only entities modified after that timestamp
3. Receiving device updates store and sends `SYNC_ACK`

## Cloud Storage Integration

No built-in cloud APIs. User downloads the `.mabak` file and saves it via OS file dialog.  
This preserves anonymity — no third-party API keys, no cloud provider trust.

## Security Considerations

| Threat | Mitigation |
|--------|------------|
| Backup file stolen, password weak | TOTP adds second factor; PBKDF2 600K iterations slow brute force |
| Device stolen | Device key stored encrypted with device-bound key; remote device removal possible from paired device |
| Server compromise | All data end-to-end encrypted; server only relays signaling messages |
| Man-in-the-middle during pairing | QR contains ephemeral key; P2P channel is DTLS-encrypted |
| Master key compromise | Per-device sub-keys limit blast radius; compromised device can be unpaired |
| Mnemonic phrase stolen | Like losing master password — TOTP does not protect mnemonic (by design, for recovery) |
